# Hades Agent 0.0.3 Plan

**Status:** planning only. Nothing in this document has been implemented.
**Baseline:** `b626316`, version 0.0.2, 668 passing / 0 failing / 13 ignored across 31 suites (re-run under the workspace memory ceiling at revision time).
**Repo:** `/home/sc/hades-agent-fresh`
**Scope:** two things, in order. First, the parts of Prime Agent's model worth adopting. Second, an appended design for a harness that rewrites parts of its own Rust runtime, verified and swapped under a satellite supervisor.

**Revision 2 review note.** An adversarial read-only critique (delegation `deleg_999ae424`) checked this plan against `b626316`: 23 findings, 7 blockers. Every load-bearing finding was re-verified against the tree before being applied. The blockers changed the design in four places: admission handles moved from the daemon (which owns no jobs) to a gateway child registry; the schema bump was removed entirely in favour of Meta-typed events so mixed generations can share a state directory; the satellite became the single owner of the gateway process and of the canary; and the snapshot was narrowed to a quiesced state set that excludes the control plane and the Telegram offset. The dispositions are in the appendix, where each accepted finding names the task that absorbs it.

## Trust posture (design premise, not a setting)

The orchestrator is trusted with the machine. Seth runs this box as a server for the agent, and a power user doing real engineering and research should expect the same: the main agent is not a chatbot in a cage.

- It runs as the user, with the user's full reach: shell, filesystem, network, services, package manager, configuration, other processes.
- It has no artificial tool allowlist. The main agent may use every tool the build ships, and may run any command the user can run.
- Subagents get a scoped slice of tools and a root for the job they were given. That is capability minimisation for a task, not distrust of the orchestrator, and the orchestrator can hand a child more when the job needs it.
- Policy gates exist to keep a *job* inside its brief and to keep an *update* inside its gate. They are not there to contain the main agent.
- The install docs must say this in the first paragraph, so nobody enables a server-resident agent thinking it is sandboxed.

The consequence for Part II is stated up front: if a generation is bad, it can do anything the user can. That is why the update path needs canaries, snapshots and rollback, not why the agent needs to be caged.

# Part I: What to take from Prime Agent

Prime Agent's two abstractions are the RLM (context as variables, tools and subagents as calls in a persistent IPython kernel) and the Continual Harness (durable prompts, memories, skills and subagent specs refined in small, rollback-able updates). We already took the recursive spawn idea. Four more things work well and fit our architecture without importing the kernel.

## What we take, and why it fits

1. **Admission handles instead of blocking spawn.** Prime's `rlm()` returns a typed handle as soon as the child is admitted, and the child's answer arrives later as a message or a file. Our `spawn` blocks until the child returns JSON (`agent.rs:1190` calls `run_child` inline). Blocking is simpler to verify but it serializes the tree and makes long children useless to a parent that could be doing other work.
2. **Agent-to-agent messages.** A handle is only useful if there is a channel. Prime lets running agents discover each other, exchange messages and steer work. Our children are call-and-return only.
3. **Persistent goals and heartbeats.** Prime keeps an objective active across turns and can re-enter a session on a timer. We have cron jobs that start new work, but no first-class goal attached to an existing session.
4. **Autonomous budgets with explicit gates.** Prime's `/autonomous` continues within turn, token and time budgets and can run user-defined quality gates, and it says plainly that reaching a limit is not success. Our `Bounds` is attempts, minutes and branch width (`graph.rs:116-129`), with no token budget and a free-text reason rather than a typed cause.
5. **Refine-style versioned harness state.** Prime's `/refine` proposes small, evidence-backed updates to supplemental prompts, memories, skills and subagent specs, records the history and supports rollback, and never rewrites the immutable base prompt. We have `hades tune`, which does this for prompt files with a floor and a holdout check. The same shape should cover skills and subagent specs.

## What we deliberately do not take

- **The IPython kernel as the action space.** It is excellent for context folding, and it is also model-generated code running with the user's permissions. Prime says so itself. Our typed tools with job-scoped capabilities are the part of Hades worth protecting, while the orchestrator itself keeps the full toolset.
- **Open-ended self-modification through `/refine`.** Part II adds code-level evolution, but under a much harder gate than a prompt edit.
- **Silent model fallback.** Prime fails a spawn if the exact model is unavailable rather than quietly choosing another. That behaviour is better than ours.

## Workstream A: admission-handle spawn

**Objective:** `spawn` returns a child id immediately; the result arrives as a message; depth and allowance rules are unchanged.

**Design notes:**
- **Correction from revision 1.** The daemon owns no jobs and no chat loop. Its own module docs say it owns no state of its own (`daemon.rs:6-10`), and `submit` assembles a graph `Runner` (`daemon.rs:456-458`, `544`), not a tool-using conversation. Cron jobs live in `<state>/jobs` and are run by the gateway's scheduler (`gateway/mod.rs:1249-1290`), which parses a schedule and records retries; that is the wrong shape for a one-shot child. Admission handles therefore get a small **child registry** in the gateway: `<state>/children/<id>.json` plus one executor thread per admitted child, calling the existing `agent::answer` (`agent.rs:536`). Cron is untouched.
- The child record holds `id`, `parent`, `session`, `chat`, `state`, `result_path`, `started`, `ended`. A child is owned by the gateway process and the parent holds only an id.
- `spawn` returns `{child_id, session, state:"admitted"}` as soon as the record is written and the executor is started. A gateway-wide cap (default 16 live children) refuses admission with a typed `busy` fault rather than starting an unbounded number of threads.
- `tell`, `children` and `result` are agent tools backed by the registry. `tell` on a finished child is refused, not queued.
- A child may spawn further, up to `MAX_SPAWN_DEPTH` (currently **2**, meaning three levels: person, worker, worker's worker; `agent.rs:468`). Every model call still draws from the parent's `Allowance` (`agent.rs:20-43`, `74-75`).
- `result` has its own hard wall-clock timeout. The run's `Bounds` are checked only at the `Failed` edge and before an exhausted decision (`graph.rs:736`, `746`) and cannot interrupt a call in flight, so relying on them would be a false promise.
- **Honest limit:** children live in the gateway process. A gateway restart ends them, and startup marks every `admitted` or `running` record as `lost` with the reason. Cutover therefore treats live children as in-flight work and refuses to proceed until they finish or a person forces it. Daemon-hosted chat children are a 0.0.4 question, not a hidden feature of this work.

**Files:**
- `rust/harness/src/agent.rs` (`spawn` at 435/823/1132, `run_child` at 957, `MAX_SPAWN_DEPTH` at 468)
- `rust/harness/src/gateway/children.rs` (new: registry and executor)
- `rust/harness/src/gateway/mod.rs` (startup recovery, drain count)

**Tasks:**

- **A0.** Add the child registry and executor in the gateway: `<state>/children/<id>.json` with the fields above, a thread per admitted child calling `agent::answer`, and startup recovery that marks stale `admitted`/`running` records `lost`. No daemon changes, and no change to cron. Test: a child record is written and its executor starts before the first model call; a registry file left by a killed process is marked `lost` on the next start, not resumed silently.
- **A1.** Record child lifecycle as `Kind::Meta` events with a `type` discriminator (`child_admitted`, `child_message`, `child_result`). **No schema bump.** `SCHEMA_VERSION` stays 1 (`session-tree/src/lib.rs:23`), because the store rejects any other version (`store.rs:80-87`) and a mixed-generation state directory would otherwise lose every session. Test: an old reader ignores unknown Meta `type` values; a Meta event with an unknown type round-trips and is ignored.
- **A2.** Add the `spawn` tool path that writes a child record and returns the handle before the first model call. Test uses a barrier in the scripted model, not a wall-clock threshold: the handle returns while the child is provably still blocked; a 17th live child is refused `busy`.
- **A3.** Add `tell`, `children` and `result`. Test: a running child sees a message on its next turn; `result` returns the validated JSON and times out with a typed fault at the parent's deadline.
- **A4.** Keep the in-process blocking path for `hades turn` and tests, where no gateway registry exists. Test: for the same scripted child, the blocking path's typed value equals what `result` returns from the registry path; the return shapes differ by design.
- **A5.** Add the session invariant: a child's Meta events carry `parent_session`, and the parent's `child_admitted` event carries the child session id. Test: walking a parent log finds every child and no orphans.

**Acceptance:** a parent can spawn three children, do a tool call of its own, then collect all three results; total model calls do not exceed the shared allowance; a gateway restart marks live children `lost`, and cutover refuses to proceed while any are live rather than killing them silently.

## Workstream B: goals and heartbeats

**Objective:** a goal survives turns, can be resumed by the gateway heartbeat, and has a defined end.

**Design notes:**
- A goal is session state, not a cron job: `{text, state: open|paused|done|cleared, session, chat, model, check, budget, executor: chat, created, updated}`. Only `chat` is accepted in 0.0.3; `graph` is refused with a typed error rather than half-implemented. The revision 1 payload lacked `chat`, `model`, `check` and `session`, which made re-entry impossible: a job with no chat is refused outright (`agent.rs:1228-1230`).
- The gateway heartbeat thread re-enters an idle session with an open goal only when the session has no live job and the last entry is older than the heartbeat interval (default 15 minutes, configurable). It is a dedicated thread beside the cron scheduler, not a new schedule in cron.
- Heartbeat re-entry is bounded by the same `Allowance`; a goal that exhausts it is paused with the reason recorded, never silently retried.
- A goal is closed by the agent claiming done plus the goal's check passing, by a person, or by budget exhaustion. The check recorded in the goal is used, not a profile default.

**Files:**
- `rust/harness/src/gateway/mod.rs` (heartbeat thread, startup scan)
- `rust/harness/src/agent.rs` (chat executor entry)
- `rust/harness/src/cli.rs` (`hades goal set|list|pause|clear`)

**Tasks:**

- **B1.** Add the `Goal` type as a Meta event with the fields above, and legal transitions `open→paused→open`, `open→done`, any→`cleared`. Test: illegal transitions are refused with a typed error.
- **B2.** Add the heartbeat tick: every 30 s, find idle sessions with open goals and an elapsed heartbeat, and run exactly one continuation in the recorded chat. Test with a fake clock: one continuation per interval, none while a job is live, and the reply lands in the recorded chat.
- **B3.** Require the recorded check to pass before `done`. Test: an agent that claims done with a failing check leaves the goal open and records the failure.
- **B4.** Add budget enforcement. Test: a goal with a 3-call budget pauses after 3 calls and says `budget`.
- **B5.** CLI surface and docs. Test: `hades goal list` on a fixture state prints text, state and last heartbeat; no model is called.

**Acceptance:** a goal survives a gateway restart, resumes on schedule, and cannot exceed its budget.

## Workstream C: autonomous budgets and honest gates

**Objective:** a run can spend tokens and time under a declared budget, and its end says exactly which budget ran out.

**Design notes:**
- Extend `Bounds` with `tokens: Option<u64>`. `Bounds::spent` is a predicate (`graph.rs:155-157`), not an accumulator, so the token sum is an argument, not a new field named `spent`.
- `Usage` already records prompt tokens, generated tokens, millis and reasoning characters (`task.rs:56-64`), and `Run` already carries `spent: Vec<Usage>` (`graph.rs:396`). The missing piece is the budget and the typed cause.
- `Ended::GaveUp` is already `{ attempts, reason }` (`graph.rs:350`). Add `exhausted: Exhausted` where `Exhausted` is `Attempts | Minutes | Tokens`, keeping `reason` for the human sentence.
- A quality gate is the existing `Verifier`, not a second mechanism.
- **Flag correction.** `hades turn` already has `--max-tokens` as the per-call completion cap (`cli.rs:205`, `899-902`), and `turn` has no `Bounds` at all. The run budget is `--budget-tokens` on `hades run` and the daemon `submit`, alongside the existing `--minutes` (`cli.rs:3026`, `daemon.rs:503-505`). `turn` is explicitly out of scope.

**Files:** `rust/harness/src/graph.rs`, `task.rs`, `cli.rs`, `daemon.rs`, `scoreboard.rs`.

**Tasks:**

- **C1.** Add `tokens` to `Bounds` and include spent tokens in its predicate. The `Runner` sums `Usage` per attempt and passes the running total to `Bounds::spent(attempts, elapsed, tokens)` at the same two sites that already check attempts and time (`graph.rs:736`, `746`). Test: a scripted model reporting 1000 prompt + 500 generated tokens exhausts a 1200-token budget after one call.
- **C2.** Add `Exhausted` to `GaveUp` and print it in `hades explain`. Test: `explain` says `tokens`, not `attempts`, for a token-exhausted run.
- **C3.** Add `--budget-tokens` to `hades run` and `submit`, keep `--minutes`, and refuse contradictory values before any model call. Do not add a budget flag to `turn`. Test: `run --budget-tokens 0` is refused; `turn --budget-tokens` is an unknown flag.
- **C4.** Teach `scoreboard` to sum spend per run and per profile. Test: a fixture run adds to the totals without changing pass rate.

**Acceptance:** no run can end `GaveUp` without a typed cause; totals reconcile with the model's own usage numbers.

## Workstream D: refine-style versioned harness state

**Objective:** prompt, skill and subagent-spec edits are small, evidenced, versioned, rollback-able, and can never touch the base prompt or the policy.

**Design notes:**
- `hades tune` already keeps a copy under `<harness>/versions/<seconds>/`, but only two fixed names (`system.md`, `tool_guidance.md`), at one-second resolution (`tuning.rs:387-410`). A skill edit would not be captured, and two adoptions in one second collide.
- Generalise storage, not the mechanism: each adoption writes `~/.hades/control/harness/<profile>/<n>/` with a manifest listing every captured file, the source session, the check result and a parent pointer. Captured files are `system.md`, `tool_guidance.md`, and every `SKILL.md` under `<state>/skills/`; restore touches only files named in the manifest. Keep `<harness>/versions/` readable for one release, then migrate.
- `hades refine --rollback <n>` restores the files named in that generation's manifest.
- Editable: supplemental prompt files, skill descriptions, subagent specs. Not editable: `floor`, `policy`, `check`, `profile.rs` defaults.

**Files:** `rust/harness/src/tuning.rs`, `profile.rs`, `skills.rs`, `cli.rs`.

**Tasks:**

- **D1.** Add a harness-generation manifest `{id, parent, files[{path, sha256}], source_session, check, created}` and a writer. Test: two adoptions produce generations 1 and 2 with distinct hashes and a parent pointer; the manifest names every file.
- **D2.** Route `tune --adopt` through the writer and capture the full file set, not the fixed two. Test: adopting the same candidate twice is idempotent; a skill file is captured.
- **D3.** Add `refine --rollback <n>`. Test: a skill-description edit round-trips byte-identically; rollback refuses to cross a floor change.
- **D4.** Add a guard that rejects candidates touching `floor`, `policy` or the check text. Test: a candidate that edits the check is refused and the current generation is untouched.

**Acceptance:** every harness edit is a numbered generation with a manifest; rollback is one command; the floor is unreachable through this path.

## Workstream E: strict model preflight

**Objective:** a requested model that is unavailable fails loudly instead of falling through to another.

**Design notes:**
- **Correction from revision 1.** `route.rs` routes *profiles*, not models: `pick` returns a `ProfileId` and only falls back to a profile (`route.rs:62`, `129-136`). There is no model fallback there to suppress.
- Model resolution happens when the CLI or daemon turns a preset or `--model` into an `OpenAi` client (`cli.rs` around 880-905, `model.rs`). Strictness belongs there: a preflight that checks the credential and endpoint before the first call, and fails with the model name.
- If the intent is also "do not fall back to another profile", that is a separate `--strict-route` flag on `route`/`turn`, and it is optional.

**Files:** `rust/harness/src/model.rs`, `cli.rs`, `agent.rs`, `daemon.rs`.

**Tasks:**

- **E1.** Add `OpenAi::preflight()` that verifies the endpoint is configured and the key is present without spending a call. Test: a missing key fails with the model and provider named.
- **E2.** Add `--strict-model` to `turn`, `run` and `submit`; when set, no substitution is allowed. Test: a missing key or endpoint returns a fault before a session is created; a configured but unreachable endpoint fails on the first call naming that model, and it is not retried with another.
- **E3.** Document the flag in USAGE and the README. Test: `hades run --help` lists it.

**Acceptance:** no strict request can spend a call on a model it did not name.

# Part II (appended): a harness that evolves its own Rust

This is the part that does not exist yet, and it is the reason to do 0.0.3 at all. The claim to test is narrow and strong:

> Hades can be given a goal, write new Rust into a fork of its own runtime, compile and verify it in a build jail, and put the result into service under a supervisor that holds the chat transport, with the previous generation available for instant rollback and the core never touched by the evolve path.

## 2.1 Prior art, and what is actually new

I searched for systems that do each ingredient. They exist. The combination does not appear to.

| Area | Prior art | What it proves | What it does not do |
|---|---|---|---|
| Agent edits its own code | SICA, A Self-Improving Coding Agent (arXiv 2504.15228) | An agent with basic coding tools can edit its own harness and improve benchmark scores (17% to 53% on a SWE-Bench Verified subset) | Runs the edited code in the same process; no build jail, no transport supervisor, no generation rollback |
| Self-modification with empirical selection | Darwin Gödel Machine (arXiv 2505.22954), Gödel Agent (arXiv 2410.04444), Huxley-Gödel Machine (arXiv 2510.21614) | Keep an archive of self-modified variants, evaluate each, select the better one | Evaluates agents in a benchmark loop; does not deploy a new binary into a live service |
| Harness optimisation with verifiers | SBCO (arXiv 2608.10157) | Verifier-grounded optimisation of a harness beats ungrounded prompt tweaking | Optimises configuration, not compiled runtime code |
| Safety of experience-driven self-evolution | On Safety Risks in Experience-Driven Self-Evolving Agents (arXiv 2604.16968) | Benign experience can still degrade refusal behaviour; self-evolution needs a safety gate independent of the experience | No deployment mechanism |
| Hot code replacement in a VM | Erlang/OTP release handling | Two module versions can be loaded, with a `code_change` callback and a release handler that can roll back | Requires a BEAM and a human-authored release; Erlang has a stable module ABI that Rust does not |
| Hot reload in Rust | `hot-lib-reloader`, Dioxus `subsecond` | A running Rust process can reload a dylib or patch functions | Development tools; Rust has no stable ABI, and changing struct layout across a reload is undefined behaviour |
| Sandboxed dynamic code | Wasmtime component model | Untrusted code can run with capability-based imports and deterministic limits | Wasm guest, not native Rust; a different performance and access profile |
| Atomic updates with rollback | Android A/B OTA, Chrome component updates, Nix generations | Slot-based updates with a known-good previous image and automatic revert | OS or app images, with no model authoring the change |

**Honest novelty statement.** Every mechanism above is old. What I cannot find shipped or described is the composition: a model writes native Rust for its own runtime; a separate verifier and a compiler decide whether it is admissible; the artifact is a content-addressed generation; a supervisor that owns the messaging transport performs the cutover and the rollback; and a compiled-in safety core keeps the update path's own machinery outside the diff. Call it novel composition, not novel mechanism. Absence of evidence is not proof, and this plan treats it as a hypothesis to test, not a claim to market.

## 2.2 Why binary swap rather than in-process hot reload

Rust has no stable ABI. A `cdylib` that exchanges structs with the host is only sound when both sides are built by the same compiler with the same layout, and a model-authored change can silently alter a struct that the host passes across the boundary. `hot-lib-reloader` and `subsecond` are excellent development tools, and both are explicit about their limits.

The safe unit of change is therefore the **process**, not the function:

- compile a new binary;
- prove it with tests and a canary;
- start it;
- keep the old binary on disk;
- switch back by starting the old one.

This is also why the satellite exists. A process swap has a gap of a second or two. The gap must not lose messages.

## 2.3 Architecture

```
                    Telegram Bot API
                           |
                    (one long poll only)
                           |
                 +---------v----------+
                 |  hades-satellite   |   fixed binary, outside generations
                 |  owns update offset|
                 |  buffers, acks     |   also runs the canary
                 |  owns the gateway  |
                 +----+----------+----+
                      |          |
        unix socket   |          |  spawn, drain, health-check, rollback
   (updates + acks)   |          |
                 +----v----+  +--v-------------------+
                 | gateway |  | generation manager   |
                 | child   |  | symlink + manifest   |
                 +----+----+  +----------+-----------+
                      |                  |
                      | unix socket      | builds in a worktree
                 +----v----+        +----v-----------+
                 | daemon  |        | evolve runner  |
                 | sessions|        | model + gates  |
                 +---------+        +----------------+
```

**Control plane versus state.** Revision 1 put the snapshot and the control plane in one tree. They are now separated by an explicit set, not by moving the existing install: a state migration in the same release that introduces generations would confound every failure.

```
~/.hades/
  control/                     never snapshotted, never restored by rollback
    bin/hades-satellite        fixed path, installed from the release
    bin/hades-evolve           fixed path, runs the gates (not `current`)
    bin/current -> generations/<id>/hades
    generations/<id>/{hades, manifest.json, patches/, build.log}
    satellite/offset           Telegram watermark
    canary/                    fixtures and per-case results
    harness/<profile>/<n>/     harness generations (Workstream D)
    evolve/<id>/               worktrees
  sessions/  jobs/  children/  mneme.db  approvals.jsonl  activity.jsonl  cron/  attempts/  inbox/
                               existing state, kept where it is, snapshotted by name
  gateway/telegram.json        legacy offset, read once during migration
  daemon.sock  daemon.json  .env  browser/  h3-gate/  mneme/
```

A later release may move the state paths under `state/`; 0.0.3 does not, because every unit, config and doctor check already names the current locations. `control/` is the only new tree.

`systemctl --user` runs two units only: `hades-daemon.service` and `hades-satellite.service`. The satellite spawns the gateway child itself. `hades-gateway.service` is retired in S2 (stopped, disabled, masked) so there is exactly one restart authority for the gateway: the satellite. If the satellite dies, systemd restarts the satellite, which then starts the gateway; systemd never starts the gateway directly.

**Satellite.** It is the only process that calls `getUpdates`. It serves updates to the current gateway child over `~/.hades/control/satellite.sock`, requires an ack per update, and advances the watermark only when every earlier update is acked. It buffers when no gateway is attached (memory, then a spill file, capped at 5,000). It runs the canary. It never renders, never decides policy, never edits sessions.

Why it must own the poll: a Telegram bot has one update stream. A second consumer or an active webhook gets a 409, and a supervisor that only restarts a gateway would still lose the updates that arrive during the gap, because the offset advanced before they were handled. Owning the offset is the only way to make the handoff lossless. The satellite records `getWebhookInfo`, calls `deleteWebhook` at startup, and refuses to start if a webhook remains or another consumer is polling.

**Generations.** Every built binary is stored, never overwritten:

```
control/generations/<id>/
  hades
  manifest.json      id, sha256, base_commit, patch_sha, created, tests, evals, effects, signature?
  patches/0001-*.patch
  build.log
```

`control/bin/current` is the only path the daemon unit and the satellite's gateway child use. A running process keeps the inode it started with. Generations are built with `cargo build -p hades --release`: the satellite is never rebuilt from a generation tree. `hades update --from` becomes "stage this file as a new generation" and refuses to modify anything under `generations/`.

**Evolve runner.** `hades evolve "<goal>"`:

1. `git worktree add control/evolve/<id> <annotated-tag>` in the source checkout named by `--repo` (or `evolve.repo` in config), from a pinned tag, never from `main`. The base commit is recorded.
2. Ask the model for a patch, using the same `patch` tool, with the worktree as root.
3. Run the gates. On failure, feed the compiler or test output back and retry, up to 3 build attempts, each within a model-call and token budget.
4. Build with `cargo build -p hades --release --locked --offline` inside a write jail, under `systemd-run --user --scope -p MemoryMax=8G`.
5. Stage a generation with a manifest.
6. Ask the satellite to run the canary and, on a pass, `PREPARE` the cutover.
7. The satellite drains, swaps, health-checks, and either keeps the new generation or restores the previous one.

**Safety core.** A compiled-in list, defined once in `rust/core/src/paths.rs` and compiled into both the satellite and the pinned evolve binary. The crate is added by a human in S2; the evolver cannot change it. A diff touching any path in the list is refused before a build starts:

```
rust/harness/src/lib.rs
rust/harness/src/main.rs
rust/harness/src/tool.rs
rust/harness/src/policy.rs
rust/harness/src/cage.rs
rust/harness/src/path.rs
rust/harness/src/approval.rs
rust/harness/src/boundary.rs
rust/harness/src/service.rs
rust/harness/src/generation.rs
rust/harness/src/ext/mod.rs
rust/harness/src/evolve/**
rust/satellite/**
rust/core/**
rust/Cargo.toml
rust/*/Cargo.toml
rust/*/build.rs
rust-toolchain.toml
.cargo/config.toml
```

`lib.rs` is in the list because `pub mod policy;` can be re-pointed at another file while `policy.rs` stays byte-identical (`lib.rs:69`). The gate runs from the satellite and the pinned evolve binary, on the patch bytes, not from `current`: after S4 `current` may itself be model-authored. Changing the list is a human commit to the satellite.

The core list constrains **the evolve path only**. It is not an OS boundary: the main agent has shell and can edit anything a human can. A change made outside the pipeline is a normal privileged action, recorded in the ledger, and it is not prevented by this design.

## 2.4 Gates, in order

1. **Core gate.** No protected path in the diff, evaluated by the satellite on the patch bytes at `PREPARE`, with `git diff --name-status -M` so a rename is treated as delete plus add. Hard fail, no retry that removes the path.
2. **Dependency gate.** In 0.0.3, no `Cargo.toml` and no `Cargo.lock` change is admissible. There is no allowlist. Adding a dependency is a human commit outside the evolve path.
3. **Static gate.** `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings`. `unsafe` and `include!` in added lines are refused. `std::process::Command` and `std::net` are allowed only in the existing seam files (`fetch.rs`, `command.rs`, `browser.rs`, `gateway/`, `daemon.rs`, `httpd.rs`, `http.rs`, `mcp.rs`, `service.rs`); a new file may not introduce them. This is a cost barrier, not a proof; see the threat model.
4. **Test gate.** `cargo test --workspace` with the unmodified test suite. Existing test files are hashed against `rust/core/test_hashes.txt` and may not be edited or deleted. New tests are welcome.
5. **Behaviour gate.** The canary, run by the satellite, not by the candidate.
6. **Canary.** The satellite starts the candidate as a subprocess with fixtures on stdin and fds, never as a path it can read, and scores the outcomes itself. Require N of M cases, no scoreboard regression, and the goal's check passing. A real-model smoke run is included within a token budget.
7. **Cutover.** The satellite drains the gateway, swaps `current`, starts the new child, waits for `HELLO` and three `PONG`s within 15 s, and either keeps it or restores the previous generation and says so in chat.

## 2.5 Threat model

| Threat | Mitigation | Residual risk |
|---|---|---|
| The model edits the cage or policy, including via `lib.rs` | Compiled-in core list, evaluated by the satellite on patch bytes; `lib.rs`, `main.rs`, `tool.rs` included | A human could still approve a bad core change; that is a review problem, not an autonomy problem |
| The gate enforcer is itself a past generation | Evolve runs from `control/bin/hades-evolve`, the satellite re-runs the core gate, and neither is rebuilt by a generation | With full machine access the agent could replace both outside the pipeline; that is a logged privileged action, not a guarantee |
| The model weakens the tests | Existing test files hashed and read-only; new files allowed | A passing new test can still be meaningless; the behaviour gate covers this |
| Malicious code in a "safe" file | Static scan plus review | A determined generator can hide a call behind a macro; the scan is a speed bump |
| Build script runs arbitrary code | `build.rs` changes are core; dependencies frozen; build is `--offline` | An existing build script could already be malicious; supply chain is out of scope here |
| A build script poisons the shared cargo cache | The jail's writable roots are the worktree target, the worktree tmp and `$CARGO_HOME`; the manifest records the build | `$CARGO_HOME` is writable because cargo needs its lock; a vendored build is the 0.0.4 fix. Until then a malicious build can affect later builds on the same box |
| A generation binary does not match its patches | The manifest records the binary hash and the patch hash; the satellite re-runs the core gate over the patches and canaries the binary | The satellite does not reproducibly rebuild the binary, so a compromised evolve runner could stage a binary whose patches look clean. A reproducible rebuild is the 0.0.4 fix; until then the canary and the pinned evolve runner are the evidence |
| Canary is graded by the candidate | Satellite runs the canary and scores outcomes; fixtures over fds, not a directory path | Same uid can read anything on disk; "held-out" means not in the prompt, not invisible |
| A bad generation acts with full machine access | Canary, gates, a quiesced snapshot before cutover, previous generation retained, automatic rollback | Rollback restores the binary and, only inside the stated window, the state snapshot, not every side effect. A destructive command already run stays run. Backups are the answer here, not a cage |
| Data written by a bad generation survives rollback | Snapshot the explicit state set; restore it after stopping daemon and gateway | Anything written outside the state set is not covered; the backup policy is the user's |
| Rollback rewinds the Telegram offset or the symlink | Snapshot excludes `control/` and `gateway/telegram.json`; test asserts the offset is byte-identical after a rollback | A restored state directory can still contain a stale job that a new gateway must reconcile |
| Rollback loop (new build crashes, old build also fails) | Satellite keeps the last known-good generation and stops after two failed cutovers, reporting rather than looping | A corrupted state directory can defeat both |
| Reward hacking the canary | Satellite-run fixtures, N of M cases, per-case verdicts in the manifest, scoreboard deltas | Small samples are noisy; a human review is still required for a `stable` promotion |
| Silent divergence from upstream | Worktrees based on annotated tags; patches exported with `git format-patch`; a conflicting patch disables the generation until rebased | A long-lived fork drifts; acceptable if patches stay small |

**The honest limit.** Full machine access is the product, so this design does not pretend to contain the agent. The gates protect the *decision to change the runtime*: they make a generation reviewable, hashed, canaried and reversible. They do not make arbitrary Rust safe, and they do not stop the main agent from running anything the user could run. A user who wants containment should run the whole install in a VM or a container, and should know that is a different product from this one.

## 2.11 Sequencing

Stages, not calendar estimates. A stage ships when its acceptance checks pass; a later stage may not start on an unproven earlier one.

- **S0, prerequisites.** Tag `v0.0.2`, commit `rust-toolchain.toml` and `.cargo/config.toml`, propagate `CARGO_TARGET_DIR` in the units. No behaviour change.
- **S1, Part I.** Workstreams A, C, E. Small, testable, no deployment risk. B and D can follow in the same stage if A lands cleanly.
- **S2, transport and generations.** F, G, service migration, plus the human-built extension seam: `rust/harness/src/ext/mod.rs` (core) defines the registry and calls `ext/generated.rs::register`; `ext/generated.rs` is non-core and is the only file the first evolved patch may touch. No self-editing yet. Prove zero lost updates, one restart authority, a real state snapshot and a rollback that leaves the offset alone.
- **S3, the loop, restricted.** I, J1-J3 (satellite canary and scoreboard gate), then H, restricted to `ext/generated.rs`, which registers one tool. The canary must exist before H8 can ask for it. Prove the whole path end to end on a change that cannot hurt the core.
- **S4, general patches.** Non-core patches, J4-J5 (chat report, real-model smoke), retry loop, patch rebase on release updates. This is the version that can fix its own build errors.

The restriction in S3 is deliberate. The first evolved change should be additive and boring: one tool in `ext/generated.rs` behind a registration seam a human built. If the pipeline cannot ship that safely, it is not ready for anything larger.

## 2.12 Open questions

1. **Daemon cutover.** The daemon owns live runs. Proposal: swap only at idle in 0.0.3, with `doctor` naming what blocks it. A run handoff protocol is 0.0.4 work.
2. **Generation retention.** Every generation carries a full binary (about 7 MB). Proposal: keep the last 5, plus `current`, `previous`, and any generation named by a manifest.
3. **Patch lifetime.** Proposal: local patches exported with `git format-patch`; `hades evolve --export` opens a PR only when asked; nothing merges to `main` by itself.
4. **Signing.** Revision 1 said "signed" and then left it unsigned. Proposal: content-addressed and hashed in 0.0.3, with an optional Ed25519 signature only for a `stable` channel a human promotes; a key on the same disk is casual-tamper resistance, not a boundary.
5. **Dependencies.** No dependency changes in 0.0.3. Revisit when there is a vendored mirror and a review process.
6. **Does the satellite ever update?** Never by the evolver. It is installed from the release and rebuilt only by a human.
7. **Sudo.** The agent gets whatever the user has. If passwordless sudo exists, it can use it and the ledger records the command; nothing here manufactures privilege.
8. **Child survival.** Gateway-hosted children die with a gateway restart. Do long-running children need the daemon-hosted chat executor in 0.0.4, or is refusing cutover while they run enough for now? Proposal: refuse cutover in 0.0.3, revisit after real use.

## 2.13 What success looks like

- A goal like "add a `json_query` tool that evaluates an RFC 6901 pointer against a JSON file" produces a generation that passes the full suite, a satellite-scored canary and a cutover, with no human editing code. (Revision 1 used `fetch_json`, which already exists as `fetch.rs`.)
- A deliberately broken proposal is refused at the core, dependency, static or test gate, and `current` never moves.
- A patch that re-points `pub mod policy` from `lib.rs` is refused at the core gate.
- Killing the new gateway mid-cutover restores the old one and says so in the chat; the Telegram offset is byte-identical afterwards.
- The Telegram offset survives every restart with zero lost updates and zero duplicate answers.
- Every applied change is a patch on disk, a manifest with hashes and canary counts, and a session log that explains why it was allowed.
